SafeGuard AI: Industrial Emergency Alert System

PROBLEM STATEMENT & VERIFIED INTENT

In industrial environments, workers need a simple, reliable way for personnel to trigger a visible and audible emergency alert that remains active until manually reset. SafeGuard AI is my first ESP32-based industrial safety monitoring project. It explores how connected hardware and software interfaces can work together to support safety monitoring, device visibility, and alert management.

PROJECT 001 // SAFEGUARD AI

SafeGuard AI — Project Specification & Dev Log

1. Overview & Problem Statement

Industrial environments present hazardous conditions where workers require an instantaneous, foolproof emergency signaling mechanism. The physical alert must latch permanently upon trigger—whether initiated by a physical mushroom button or an automated computer vision alarm—and remain active until an operator deliberately activates the reset sequence.

2. Hardware Bill of Materials (BOM)

Component Specification / Part GPIO Assignment Role
Microcontroller ESP32-WROOM-32 DevKit (Dual-core 240MHz) Internal Core finite state machine & UART telemetry
Emergency Switch Normally-Open Push Button (SPST Momentary) GPIO 18 (Input Pull-up) Latches system into EMERGENCY alert state
Reset Switch Normally-Open Push Button (SPST Momentary) GPIO 19 (Input Pull-up) Clears alert and restores NORMAL state
Red LED 3mm High-Intensity Red LED + 330Ω Resistor GPIO 22 (Output) Visual emergency indication (REQ-004)
Green LED 3mm Green Status LED + 330Ω Resistor GPIO 21 (Output) Visual normal state indication (REQ-002)
Audio Buzzer 3.3V Active Piezo Buzzer Module GPIO 23 (Output) Audible high-decibel alarm pulse (REQ-004)

3. Firmware State Machine Architecture (ESP-IDF v5.5)

The ESP32 firmware is structured as a non-blocking deterministic finite state machine implemented in C/C++:

  • STATE_NORMAL: Boot default state. Green LED driven HIGH, Red LED driven LOW, Buzzer driven LOW. Serial broadcast: [STATUS] NORMAL - MONITORING.
  • STATE_EMERGENCY: Entered when GPIO 18 interrupt fires or valid serial trigger arrives. Red LED driven HIGH, Buzzer driven HIGH, Green LED driven LOW. This state is permanently latched; releasing the emergency button has zero effect.
  • STATE_RESET: Triggered strictly by GPIO 19 press. Restores system to STATE_NORMAL and logs timestamp over UART.

4. Acceptance Tests & UART Telemetry (Verified)

Test ID Action Expected Outcome Verification Result
TEST-001 Power on board from cold boot System enters NORMAL; Green LED ON; Red LED OFF PASSED
TEST-002 Press physical emergency switch Red LED activates; Buzzer sounds; Green LED turns OFF PASSED
TEST-003 Release emergency switch Alert remains fully latched (no state reversion) PASSED
TEST-004 Press manual reset switch Alert clears; Buzzer silences; Green LED turns ON PASSED
TEST-005 Cycle emergency/reset 5 consecutive times Deterministic state transitions with no deadlocks PASSED

5. Engineering Challenges & Next Steps

Switch Chatter & Bounce: Mechanical push buttons generated dozens of microsecond contact closures per press. Rather than using crude delay loops that block execution, I implemented hardware RC debouncing alongside edge-triggered ISR handlers.

Current Limitations:

  • Fire/smoke vision inference runs on a connected host machine sending UART packets rather than directly on the ESP32 (MCU memory constraints).
  • Dashboard communication currently uses simulated REST/serial logging rather than encrypted WebSockets.
  • This device is an educational prototype and is not certified to SIL-3 or NFPA industrial safety standards.
